✅ Cumplimiento WCAG 2.1

El sistema Concorde está diseñado para cumplir con las Pautas de Accesibilidad para el Contenido Web (WCAG) versión 2.1, nivel AA. Estas pautas se organizan en cuatro principios fundamentales: Perceptible, Operable, Comprensible y Robusto (POUR).

Nivel AA

Perceptible

Todo el contenido tiene alternativas textuales. Las imágenes incluyen atributo alt. Los videos tendrán subtítulos.

Nivel AA

Operable

Toda funcionalidad es accesible mediante teclado. No hay límites de tiempo que impidan completar acciones.

Nivel AA

Comprensible

El idioma de la página está declarado. Los formularios tienen etiquetas claras y mensajes de error descriptivos.

Nivel A

Robusto

El código HTML es semántico y válido. Compatible con lectores de pantalla actuales (NVDA, JAWS, VoiceOver).

🏅 Concorde apunta al nivel AA de WCAG 2.1, que es el estándar requerido por la legislación colombiana de accesibilidad digital (Ley 1618 de 2013).

🔎 Heurísticas de Nielsen aplicadas

El diseño de las interfaces de Concorde sigue las 10 heurísticas de usabilidad de Jakob Nielsen. A continuación se explica cómo se aplica cada una dentro del sistema.

1

Visibilidad del estado del sistema

El sistema mantiene informado al usuario sobre lo que ocurre en todo momento mediante respuestas visuales apropiadas y en tiempo razonable.

Ejemplo: El stepper de compra (Buscar → Detalle → Pasajero → Asientos → Pago → Confirmación) muestra exactamente en qué paso se encuentra el usuario y cuáles ha completado.
2

Correspondencia entre el sistema y el mundo real

El sistema habla el lenguaje del usuario, usando palabras, frases y conceptos familiares para el contexto del transporte terrestre en Colombia.

Ejemplo: Se usan términos como "tiquete", "terminal", "ruta", "pasajero" y moneda en pesos colombianos ($), no términos técnicos.
3

Control y libertad del usuario

Los usuarios pueden deshacer y rehacer acciones fácilmente. Siempre hay una salida claramente marcada cuando eligen funciones por error.

Ejemplo: En cada paso del flujo de compra existe el botón "Regresar". La cancelación de reservas permite al usuario rectificar su decisión.
4

Consistencia y estándares

Los usuarios no tienen que preguntarse si diferentes palabras, situaciones o acciones significan lo mismo. Se siguen las convenciones de la plataforma.

Ejemplo: Los botones primarios siempre son azules, los de cancelar siempre son rojos, y la navegación siempre está en la misma posición en todas las pantallas.
5

Prevención de errores

Se diseña cuidadosamente para evitar que ocurran problemas en primer lugar, eliminando condiciones propensas a error o presentando confirmaciones.

Ejemplo: El mapa de asientos muestra visualmente cuáles están ocupados antes de intentar seleccionarlos. El formulario de pago valida el número de tarjeta en tiempo real.
6

Reconocer antes que recordar

Se minimizan la memoria del usuario haciendo visibles los objetos, acciones y opciones. El usuario no tiene que recordar información entre pantallas.

Ejemplo: El resumen lateral del viaje (ruta, fecha, precio) se muestra de forma persistente durante todo el flujo de compra.
7

Flexibilidad y eficiencia de uso

Los aceleradores permiten a los usuarios frecuentes realizar acciones más rápidamente. El sistema atiende tanto a usuarios inexpertos como expertos.

Ejemplo: El buscador en la página de inicio permite buscar directamente sin necesidad de registrarse. Los usuarios registrados tienen sus datos prellenados.
8

Diseño estético y minimalista

Los diálogos no deben contener información irrelevante. Cada unidad de información adicional compite con la información relevante.

Ejemplo: Las tarjetas de resultados de viaje muestran solo la información esencial: hora, ruta, duración y precio. Los detalles se revelan al hacer clic.
9

Ayuda al reconocimiento, diagnóstico y recuperación de errores

Los mensajes de error se expresan en lenguaje claro, indican el problema con precisión y sugieren una solución constructivamente.

Ejemplo: Si el pago es rechazado, el sistema muestra exactamente qué verificar (datos de la tarjeta) sin tecnicismos, y ofrece intentar de nuevo.
10

Ayuda y documentación

Aunque es mejor que el sistema pueda usarse sin documentación, puede ser necesario proveer ayuda que sea fácil de buscar y orientada a la tarea.

Ejemplo: El módulo PQRS permite al usuario contactar soporte cuando algo no queda claro. Los formularios tienen textos de ayuda (placeholder) en cada campo.

⌨ Navegación por teclado

Toda la funcionalidad del sitio es accesible únicamente con el teclado, sin necesidad de ratón. El orden de tabulación sigue la estructura lógica visual de la página.

📝 Formularios accesibles

Todos los formularios del sistema aplican prácticas de accesibilidad para garantizar que cualquier usuario pueda completarlos correctamente.

WCAG 1.3.1

Etiquetas visibles

Cada campo de formulario tiene una etiqueta <label> vinculada, visible y descriptiva, nunca solo placeholder.

WCAG 3.3.1

Identificación de errores

Cuando se detecta un error de entrada, el elemento con error se identifica y el error se describe al usuario en texto.

WCAG 3.3.2

Instrucciones de campo

Los campos que requieren formato específico (ej. teléfono, fecha) incluyen un ejemplo en el placeholder o texto de ayuda.

WCAG 3.3.4

Prevención de errores

Las acciones importantes como pagos y cancelaciones requieren confirmación antes de ejecutarse, permitiendo revisar y corregir.
